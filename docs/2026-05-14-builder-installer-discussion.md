# Builder + 首次安装器方案讨论记录

日期：2026-05-14

## 这次讨论的核心问题

目标不是只解决“我自己这台电脑怎么打包”，而是要考虑如何把这套 Pake 工作区分享给别人，让别人也能：

- 不用跑 `npm install`
- 尽量不用理解 `cli` 内部结构
- 主要只改：
  - `project.json`
  - `inject.css`
  - `inject.js`
- 然后执行一个入口，就能重新打包得到 exe

## 已确认的结论

### A 方案：自己本机使用

这个其实已经基本实现了。

当前工作区已经支持：

- 在 `projects\某项目` 中修改 `project.json`
- 修改 `inject.css` / `inject.js`
- 双击项目里的打包脚本
- 最终得到 exe/msi

所以后续重点不再是 A，而是 B。

### B 方案：分享给别人使用

真正的问题是：

- 别人拿到工作包后，能否也这样改配置后直接打包

这里又分成两档：

1. 对方机器允许先装一次 Rust/Tauri 等环境
2. 对方机器完全不装 Node / Rust / Tauri / cargo / VS Build Tools，也能直接重新打包

用户本轮明确想讨论的是第 2 档。

## 对“完全免安装”的判断

结论：理论上可以逼近，但很难做成真正稳定、通用、完全绿色。

原因是：

- 当前 `cli` 不是最终编译器，只是构建调度层
- 它会继续驱动 Tauri / cargo / Rust 构建链
- 真正产出 exe 的核心能力不在 `node cli.js` 本身，而在 Rust/Tauri/Windows 工具链

所以把 `cli` 打成 exe，并不等于可以完全摆脱系统级构建依赖。

## 讨论过的三条路线

### 方案 1：半便携工作包

思路：

- 把 `cli`
- Node 运行时
- 尽量多的 Rust/cargo/Tauri 构建能力
- 脚本和项目结构

一起整理进一个可分发工作包。

优点：

- 最接近“拿到就用”
- 不需要日常执行 `npm install`

缺点：

- 体积大
- 维护复杂
- 仍可能受目标机器系统环境影响

### 方案 2：远程打包

思路：

- 别人本地只改项目配置
- 打包时把项目发到服务器或 GitHub Actions
- 远端构建后把 exe 返回

优点：

- 本地几乎零环境

缺点：

- 依赖网络
- 依赖远端服务
- 维护成本高

### 方案 3：本地 builder.exe + 首次安装器

思路：

- 给用户一个统一入口，例如 `builder.exe`
- 第一次运行时做环境检查
- 如缺依赖，执行安装/初始化
- 之后用户只改项目配置并点击打包

这一轮讨论后，方案 3 被认为比“纯便携方案”更现实。

## 当前推荐方向

当前更推荐：

- 本地 `builder.exe`（或先用脚本版 builder）
- 配合“首次安装器”
- 面向自己和少数熟人 Windows 机器使用

明确不追求：

- 面向完全不懂环境的广泛普通用户
- 完全零权限、零系统依赖、任意机器绝对稳定

明确追求：

- 首次准备一次环境
- 后续只改项目配置和注入文件
- 之后项目目录双击即可打包

## 关于分发对象的确认

本轮已确认：

- 目标分发对象是“自己或少数熟人 Windows 机器”
- 可以接受首次安装时点几下
- 也可以接受在必要时出现管理员权限

这意味着方案不需要产品化到面向大众用户的程度，优先考虑：

- 可维护
- 稳定
- 易排障

## builder + 首次安装器的建议架构

### 推荐整体思路

先做：

- 统一 builder
- 统一环境检查
- 统一初始化脚本

之后再决定是否把 builder 脚本封成真正的 `builder.exe`。

### 推荐演进路线

推荐顺序：

1. 先做 `builder.cmd/.ps1` + `setup.ps1`
2. 把整条链路跑通
3. 再把入口封装成 `builder.exe`

原因：

- 先验证流程是否可用
- 先解决真正的环境与构建问题
- 不要太早把精力消耗在“包装成 exe”上

## 推荐目录结构草案

```text
pake-kit/
  builder/
    builder.cmd
    builder.ps1
    doctor.ps1
    setup.ps1
    config.json
  runtime/
    node/
    pake/
      dist/
      src-tauri/
      node_modules/
  projects/
    template/
    app1/
    app2/
  releases/
```

## 各目录职责

### `projects/`

给最终使用者看的，只保留项目层内容：

- `project.json`
- `inject.css`
- `inject.js`
- 项目级 `build.cmd`

### `builder/`

统一入口，负责：

- 接收项目路径
- 读取项目配置
- 检查环境
- 缺依赖时触发初始化
- 触发构建
- 收集产物到 `dist` / `releases`

### `runtime/`

放内置运行时和本地 Pake 构建层：

- Node
- `cli/dist`
- `cli/node_modules`
- `src-tauri`

### `releases/`

集中存放最终成品。

## 预期使用方式

日常使用流程应当是：

1. 用户进入 `projects\某项目`
2. 修改：
   - `project.json`
   - `inject.css`
   - `inject.js`
3. 双击 `build.cmd`
4. `build.cmd` 统一调用：
   - `..\..\builder\builder.cmd build <当前项目目录>`

## 首次安装流程设想

第一次运行时，builder 负责检查：

- 内置 Node 是否存在
- `runtime\pake` 是否完整
- Rust / cargo 是否可用
- Windows C++ build tools 是否可用
- WebView2 是否可用

如果缺失：

- 提示是否立即初始化环境
- 执行 `setup.ps1`

`setup.ps1` 负责：

- 优先复用本机已有环境
- 缺什么补什么
- 记录状态到本地配置文件，例如 `builder\config.json`

后续运行时：

- 如果环境状态正常，则直接构建
- 尽量不让用户再接触 Node / npm / cargo 命令

## 为什么当前更倾向“首次安装器”而不是“纯便携工具链”

主要原因：

- 纯便携工具链要尽量把所有构建能力都塞进工作包
- Windows 系统级依赖不一定都能可靠便携
- builder + 首次安装器更容易处理机器差异
- 更适合固定范围分发（自己/熟人机器）
- 更容易排障和维护

## 已经明确的设计原则

### 1. 项目层与构建层彻底分离

不要再让每个项目直接依赖：

- `..\..\cli\dist\cli.js`

而应统一依赖：

- `..\..\builder\builder.cmd`

### 2. 用户日常不接触构建细节

用户平时只需要：

- 改配置
- 点构建

### 3. 首次准备成本集中处理

把复杂性尽量前置到：

- `doctor.ps1`
- `setup.ps1`

不要把复杂性散落到每个项目脚本里。

### 4. 先让流程跑通，再考虑包装成 exe

builder 是否最终封装成 exe，不应早于流程稳定。

## 当前未决问题

下次继续时，需要重点决定这些问题：

1. `setup.ps1` 应该优先“复用系统已有环境”，还是“强制安装固定版本环境”
2. Node 是否需要内置，还是可允许复用系统 Node
3. Rust / cargo 是否走系统安装，还是尽量随工作包固定版本
4. `doctor.ps1` 具体检查项和失败提示文案
5. `builder.cmd` / `builder.ps1` 的命令接口设计
6. 是否保留当前 `projects\xxx\build.ps1`，还是全部改为统一入口
7. 什么时候再考虑把 builder 封成真正 `builder.exe`

## 下次继续时的建议起点

下次可以直接从下面两个问题继续：

1. `setup.ps1` 的策略到底选哪种：
   - 尽量复用系统已有环境
   - 强制按指定版本安装固定环境
2. `builder` / `doctor` / `setup` 三个入口的命令与职责怎么切

## 一句话总结

当前阶段的共识是：

- 不再纠结“绝对零环境的纯便携包”
- 转向“builder + 首次安装器”
- 面向自己和熟人机器
- 先把统一入口、环境检查、初始化流程设计清楚
- 稳定后再考虑把入口封成 exe
